# Trusted lobby and property-action prototype

This is an **isolated development service**. Authenticated lobby admission and property actions have a default local HTTP adapter. Audited setup/dice/turn/jail/card/auction/debt/reroll/trade/end kernels and the first AI auction worker are implemented below. Human game HTTP routes now require explicit service composition; public game start, the complete playable client and production deployment remain disabled. Neither browser transport is imported by the shipped game yet.

## Token power rules version

New games now carry `tokenPowerVersion: 2` and use the 16 token-specific power paths. Saved games without that tag keep the original shared tier perks; unknown future versions are rejected. The public game projection carries the approved tag so the opt-in screen uses the same rules as the server adapter. This versioning does not activate production hosting or signed progression. See [portfolio and token mastery results](../../PORTFOLIO-TOKEN-MASTERY-RESULTS.md).

## Opt-in human lobby start

`createStartService({db, verifyIdToken, resolveRoster})` now composes verified human lobby seats into the source initializer. The required synchronous roster policy authorizes premium ownership/tier, token/finish/character choices and city/theme; no production default is supplied. `/v2/game/lobby`, `/v2/game/seat` and `/v2/game/start` are available only when explicitly composed as `gameServices.start`. The default admission start remains disabled.

Use the journaled game client for `selectSeat` and `startGame`, with the current lobby revision and no client outcomes. Recover an uncertain command with `reconcile`, fetch fresh lobby/game state, then clear only its acknowledged request ID. The committed opening is an allowlisted announcement; it cannot resample keys or pay another bonus. Timers, minigames and AI roster start remain gated in this slice. The opt-in acknowledged waiting-room controls are implemented below; public title/create/join routing is not yet migrated. See [trusted start results](../TRUSTED-START-RESULTS.md).

## Opt-in waiting-room controls

`lobby-controller.mjs` reads freshly authenticated lobby views, validates member/host/seat shape and monotonic revisions, and exposes only own-seat selection, host Start and receipt reconciliation. It reuses the journaled game transport. No client cash, tier, UID, game snapshot or dice is submitted. Server roster/ownership validation remains mandatory and is not replaced by the token catalogue supplied to the UI.

`mountLobbyControls({client, code, uid, container, tokens, onStarted, onError, pollMs})` adds an explicitly mounted waiting room to a connected container using the current game classes. Tokens are catalogue entries `{tok,label}`; the selected authoritative finish/character are retained. Names/labels use text nodes, not HTML. Start is host-only, requires two seats and is disabled for the current unsupported timer/minigame settings. A pending selection/start prevents new mutations until reconciliation plus a fresh view completes. Polling retains unchanged focused controls; detachment, close, revoked membership and account changes fail closed.

Call `await waiting.refresh()` after mounting. `onStarted(view, {client,code,uid})` owns the game handoff, using the same authenticated client. It must resolve only after it owns the game screen, and must own cleanup/retry if it partially mounts a screen before failure. Repeated callback attempts must not mount duplicate screens. The waiting room does not execute an initializer or opening animation; the source-authored canonical opening remains in the existing game projection. Successful handoff detaches the waiting-room controller without closing the shared client; ordinary close closes it. Game-action journals are left for the game controller, never settled as lobby commands.

This module is not imported by the shipped title. No public admission/create/join/invite-sharing flow or production runtime is activated. Initial board-read recovery/partial-mount cleanup in the final product handoff, source-styled opening announcement, secure admission/invite journaling, full AI/timer/minigame behavior, production roster policy and deployment remain explicit follow-ups. No release/security gate is closed by this preview.

Run `node service/lobby-controller.test.cjs` from the security directory. Browser CI runs `node skyline-estates/security/service/lobby-browser.test.cjs` from repo root against the real HTTP adapter. In a restricted local workspace, `SKYLINE_FILE_TEST=1` loads the actual page and test-only data-URL module imports and calls the actual service implementations through Playwright's local test bridge; this is not HTTP/CORS or live Firebase evidence. Emulator integration separately exercises real HTTP, Auth and Database with admitted rooms and shared operation journals.

## Recoverable room entry and private invitations

The separate `createRoomClient` in `room-client.mjs` is an opt-in HTTPS admission transport. An explicit HTTPS origin allowlist, current UID/token provider, durable storage and Web Locks are required. HTTP is accepted only for explicitly enabled 127.0.0.1 tests. The original loopback `client.mjs` remains for historical tests; the shipped title imports neither new room-entry nor game transport automatically.

Supported mutations are `create {name,settings}`, `join {name,code,invite}`, `leave {code}` and host-only `invite {code}` (replaces the active invitation). Persisted journals contain only version/origin/UID/action/request ID/request digest, optional room code and a capability-free acknowledgement. Names, settings, invitation capabilities, share links and authentication tokens are never written by this journal. Create responses/invite rotation may return a capability transiently to the current host. Join capabilities travel only in the authenticated request body. The digest uses the same canonical fields/order as server validation; tests compare actual digests.

`POST /v2/rooms/settle` authenticates the original UID and reads that account's private operation ledger. It returns the existing result or atomically records a tombstone that fences a delayed original. Recovery does not resend a create/join mutation with a fresh ID. If an undelivered join is retired, the user must supply the invitation again. Mutation acknowledgements remain pending until the caller completes their exact ID; the entry UI first reads fresh authorized membership for create/join/invite. Leave recovery deliberately works after membership is removed and exposes only the caller's receipt.

Admission ledger records now carry `admissionAction`. New settlement rejects pre-existing entries without that marker rather than guessing they are admission receipts. The older unjournaled client has no new journal to migrate; rollout still requires a reviewed ledger/incarnation/retention policy. Current-host/lobby/active-capability checks redact obsolete secrets from both normal create/invite replay and settlement. Host leave invalidates the old capability; the new host must explicitly create a replacement. Rotation and leave do not remove other already-admitted members. Invitation expiry/rotation UI policy and room/ledger TTL are not supplied by this slice.

`makeRoomInvitation`/`parseRoomInvitation` in `room-invitation.mjs` use an HTTPS URL fragment at the configured game origin/path. They reject query-string capabilities, foreign origins/paths, credentials and extra fragment fields. The fragment keeps the capability out of the request path/query; it does not protect it from same-page scripts, clipboard access or whoever receives the full private link. Do not log or send links to analytics. The helpers return a clean URL for a future router to remove the fragment; they do not change browser history or activate native Universal/App Links.

`mountRoomEntryControls({client,uid,container,gameUrl,allowedOrigins,settings,name,onRoom,onError})` explicitly mounts Create, Join-by-link, Replace invitation, Leave and recovery controls using existing classes. It validates fresh membership before displaying a room/share link. `onRoom` owns the handoff into waiting-room controls, including partial-mount cleanup; use a separately authenticated game client for the waiting room because successful entry closes the admission client. These callbacks/routes are preview composition, not automatic public-title activation. Saving/reopening a last-room pointer, production authentication wiring, mobile link association and the full reconnect/forfeit policy remain follow-ups.

## Implemented boundary

- `admission.cjs` requires a privileged database and an ID-token verifier. Identity always comes from verified authentication, never a caller-supplied UID. Token verification checks revocation/disabled status on every operation.
- A single `skylineV2` transaction commits membership/seats/revision/host changes, private operation receipts and per-UID budgets together. The prototype uses the whole subtree to prove atomicity; this is a scaling hotspot, not a production database layout.
- Room codes keep the five-character format. Joining additionally requires a 256-bit invitation capability. Only its hash is used for admission; the private idempotency receipt retains the original create response for retry recovery. Neither secrets, hashes nor receipts are returned in room views or readable by clients under the candidate rules. Invites should be shared only with intended players.
- Stable operation IDs fence retries. Same UID/ID/content returns the prior result; changed content conflicts. Private UID/operation keys are hashed to avoid JavaScript property-name collisions. Verified UID keys are restricted to safe database characters and exclude reserved prototype names.
- Server-controlled seat allocation preserves the six-seat limit, unique names and seat order. Host leave transfers ownership to the lowest remaining seat and invalidates the old invitation; the last leave closes the lobby and invalidates its invite. Leave/join during active gameplay is deliberately not enabled.
- A transactional per-UID budget includes rejected admission attempts. Replaying a retained receipt does not charge again. Gateway/IP/global abuse controls, admission quotas, invite rotation/expiration and ledger/room TTL cleanup are still required.
- Selected flat settings and house-rule booleans are preserved, with shape/known option checks. Full city/theme registry, token/progression and legal-rule validation must be enforced by the authoritative engine before a game can start. No prices, gameplay rules or artwork are changed.

## Local transport and authentication

The HTTP adapter accepts bounded JSON bodies and Authorization bearer headers, returns sanitized errors with no-store caching, and permits browser origins only from an explicit allowlist. It does not use cookies or wildcard credentialed CORS.

`emulator-runtime.cjs` refuses initialization unless both Auth and Database emulators use loopback and the exact project is `demo-skyline-phase1`. It has no production startup/deployment entry point. Firebase Admin SDK 13.4.0 is a pinned development dependency. The Auth emulator uses emulator credentials/unsigned test tokens: this verifies adapter/token-validation/account-disable plumbing, **not production signing keys, real-provider identity assurance or abuse prevention**.

Run `npm test` in `skyline-estates/security`. The CLI starts Auth and Database emulators, first checks the property kernel, evaluates the existing permission matrix, then runs `integration.test.cjs`. Two independent Admin SDK app/database connections and two HTTP services contend against the same demo database. Results are saved as `service-results.json`.

The matching client adapter accepts only a loopback HTTP endpoint, obtains the current token for every request, omits cookies and refuses redirects. Persist/generate the request ID **before** the first attempt, then reuse that ID and body after an uncertain response. Automatic retries with a fresh ID would not be idempotent. A known room can be reopened by an authenticated existing member without resubmitting its invitation.

```js
const client = createAdmissionClient({baseUrl: localEndpoint, getIdToken});
const requestId = client.requestId(); // keep this until the outcome is known
const {code, invite} = await client.createRoom({
  requestId, name, settings
});
await client.joinRoom({
  requestId: client.requestId(), code, invite, name
});
const lobby = await client.room(code);
```

This adapter is protocol work, **not a UI migration or full playable game client**. The visible short code remains a locator, not an authorization secret. The future v2 share link must carry the invitation capability; the current legacy code-only flow is unchanged until a reviewed migration.

## Property actions (isolated test snapshots only)

The action envelope contains only requestId, code, expected revision, and command {kind, square}. Identity comes from the token. Membership, authoritative seat/current turn, revision, rule legality, game/bank validity and the operation receipt are checked in the same privileged transaction. A successful action changes the stored snapshot and increments its revision once; simultaneous old-revision commands conflict. Denials retain a private receipt without altering the room. A replay returns the original acknowledgement, so read the current room after recovering an uncertain response; a receipt is not fresh room state.

Snapshots are stored as state.gameJson strings to preserve empty arrays/objects that Realtime Database would otherwise omit. Clients cannot submit snapshots, prices, actor IDs or ownership. Current room views expose lobby metadata only; a redacted gameplay projection/subscription is still needed before UI integration. The tests seed playing snapshots with privileged emulator access; no client or public endpoint can start this subset.

asset-kernel.cjs evaluates only audited sections of the checked-in game.html in an isolated per-call VM context with a time limit and dynamic code generation disabled. This is rule reuse, not a VM security boundary for untrusted source. The full normalized game source is pinned by SHA-256; any source change fails closed until hooks are audited and parity is rerun. Both basic property functions and the later construction-boom/counter hook are reused. Rendering/local profile reward hooks are disabled, while per-game construction counters remain. No production reward or entitlement authority is claimed.

Only pre/post turn phases are supported. Debt liquidation and other phases remain disabled until the complete turn/debt workflow is implemented. The 41-case real-browser parity test compares complete resulting snapshots or unchanged denials against the fully loaded game (including its later wrappers), with rendering effects suppressed. Kernel tests separately cover malformed commands/state, wrong actor, conservation, input immutability and context isolation. Integration tests use real Auth/Database emulators and two HTTP service instances for replay, concurrency, authorization and rejected-state preservation. Results: asset-results.json, service-results.json, and the stability artifact's skyline-asset-browser.json.

This subset is not a replacement for the existing live multiplayer engine. Keep candidate rules/service isolated until all approved gameplay, hidden-state projections, recovery and actual browser-client migration pass review together.

## Internal setup and randomness prerequisites

setup-kernel.cjs now reuses audited newGame, the later Skyline Keys wrapper, name cleanup, and dice-generation rules from the game source. It is an internal prerequisite, not a public start or roll implementation. initializeGame accepts an already trusted roster plus validated approved settings; it preserves Classic/Quick/timed modes, all 31 cities, existing rule flags, token/cosmetic/tier fields, two Quick Deal properties per seat, shuffled decks, unique floors 2–99, highest-key first player and the last player's +100 bonus. It does not verify ownership/entitlements: the future profile/admission boundary must supply those trusted choices. Unknown fields/registries and malformed rosters are rejected before randomness is consumed.

Fisher-Yates uses Node crypto.randomInt for unbiased integer draws rather than Math.random. The dice-generation expression uses the same trusted integer provider and preserves turbo gating after the first lap and its 1–4/star/taxi faces. Math.random throws inside these kernels, so an unaudited extra random use fails closed. The sealed-key wrapper in the original game catches exceptions; the kernel additionally requires a complete valid key draw, preventing entropy failure from returning a keyless game. An injectable integer provider exists only as an internal test dependency; no HTTP body accepts it or a seed.

sampleDice is a non-mutating primitive. It does not store a roll, increment a revision, move a player, resolve cards/rent/jail/debt, offer a perk re-roll, advance a turn or issue profile rewards. Calling it again samples again. Before any public roll/start endpoint is enabled, the service must durably bind its private random result to the authenticated request/revision, reuse it on transaction retries/recovery, and commit the complete rules transition plus receipt atomically. Never generate fresh randomness inside a retrying database transaction. Do not send a whole setup snapshot or deck order to an untrusted client; a redacted game projection is still required.

The shared audited-rules.cjs owns the full-source pin and identity checks. UID-less AI seats remain legal while human identities are mandatory and non-null identities are unique. The property subset now accepts that same legitimate AI roster shape. This does not implement AI turns, leave/reclaim or host transfer during gameplay.

Unit tests compare setup invariants and every two-/three-die value combination under all turbo/first-lap gates, reject malformed inputs and simulate entropy failure. Real-browser tests compare entire setup snapshots and exact dice values/random-call counts against the fully loaded original functions. Results are retained as setup-results.json and skyline-setup-browser.json. Public /start remains 501; roll is not an accepted command. No live service or rules deployment is introduced.

## Durable roll reservations (internal only)

roll-plans.cjs now reserves a private roll against the verified actor, exact room revision, serialized game digest and audited source hash. It uses the existing dice kernel, including turbo gating. One candidate of three crypto.randomInt values is generated before the retrying transaction; each callback starts from that same candidate. The winning transaction stores the private dice JSON, revision slot, pending-room lock, shared operation receipt and per-UID budget atomically. Competing requests can neither replace the winning slot nor select a fresh roll by changing operation ID.

reserveRoll returns an acknowledgement without dice. A repeated UID/operation/body returns its recorded acknowledgement before requiring new entropy; changed content or cross-action reuse conflicts with the shared admission ledger. loadRoll and recoverRoll require verified current membership/seat/turn plus server-acknowledged data. They check revision, exact game/source digest and stored dice validity; recovery uses the saved values and never resamples. No-op read transactions require a server acknowledgement and a deadline, so an offline cache cannot disclose dice after a peer revokes membership.

Plans/locks are under the candidate rules' denied service subtree. No HTTP route, client adapter or game UI calls these methods. Existing member room views expose neither dice nor plan IDs. The property action processor refuses new edits while a roll is pending (checking both the lock and retained revision slot if an index is missing), so a race either commits the property revision first (the roll is stale) or reserves the roll first (the edit is blocked). This adds no live gameplay change because public start/roll remain disabled.

A timeout reports an uncertain outcome, not rollback. The queued transaction may later commit; recover using the original operation ID rather than issuing a replacement. Every callback rechecks current room authority and revision. Tests cover a lost post-commit reply, delayed mutation after timeout, independent service/Admin connections, competing operations, property contention, disabled tokens and offline revocation. A recovered receipt is historical acknowledgement; only a fresh load revalidates access to the dice.

The subsequent internal movement/checkpoint slice now consumes a saved plan, retires its pending lock and commits state/revision/receipt atomically; see below. It is not complete turn resolution or public gameplay. Perk re-rolls need a separate authorized stage and budget; changing request ID is never a re-roll. A source or state mismatch fails closed pending reviewed recovery/migration.

Plan slots currently assume retained, non-reused room codes. Before room cleanup/reuse, add immutable room incarnation IDs. Do not delete reservation slots/receipts and reopen the same revision: cleanup needs durable consumed-revision watermarks and a reviewed recovery policy. Whole-subtree contention, bounded private-state retention, production quotas/authentication and full gameplay/redacted-client integration remain rollout gates. A restarted service/SDK connection is tested; database server restart/failover and production networks are not claimed.

## Internal movement and choice checkpoints

turn-kernel.cjs reuses audited movement, passing-Start/payday/perk hooks, third-double jail handling, landing/payment/rent-event/shield/counter hooks, purchase logic and currency/localization from the approved game. It removes async UI waits from those controlled source sections to produce a deterministic synchronous transaction result; it does not evaluate client-supplied code. Rendering and local profile rewards are suppressed. The original online mini-game guard remains relevant: this is not a new mini-game authority. Extra randomness is forbidden inside the kernel.

turn-service.cjs consumes an existing private roll and atomically writes the resulting game/revision, consumption tombstone, checkpoint (if needed), shared operation receipt and budget. Retrying the same operation returns its original acknowledgement. A new operation cannot reapply a consumed roll. Purchase buy/decline and perk keep choices each require current verified membership/seat/revision plus an exact checkpoint game/source digest. A purchase uses the source board price and cannot reuse consent on the taxi's second property. Completed ordinary/double rolls stop at post/pre respectively; end-turn advancement is not implemented here.

Checkpoints persist privately under service/turns, replacing the consumed roll lock while a decision is active. They fence unrelated property edits and new rolls. readDecision requires a server acknowledgement/current authority and returns only the current boundary, not the stored continuation context or deck. The method has no public route/client wiring. Restarted service instances can resume purchase/keep decisions without rerolling, moving again or charging twice. Timeouts remain uncertain; recover the original operation ID.

Implemented landing effects include affordable rent/tax payment (with existing event/shield rules), waived rent, jackpot collection and jail/Lucky Pass behavior. Unaffordable payments stop before liquidation/bankruptcy with the effective bill preserved. Cards stop before deck mutation; declining with auctions enabled stops before bidding. Eligible token re-rolls pause before movement; keep is supported, drawing a replacement is not yet implemented. Raising purchase cash, auctions, card execution, debt liquidation/bankruptcy, AI turns, authorized replacement re-rolls, end-turn/events/finish and full redacted UI/recovery integration remain explicit gates. Unsupported choices fail without changing the room; no rule is silently skipped.

The browser oracle executes the real playTurnInner with controlled original rollDice, intercepting only animation/profile effects and decision boundaries. Entire game snapshots and boundaries are compared at the initial roll and each supported continuation. Unit tests additionally force repeated transaction callbacks and check immutable inputs, conservation, once-only plan/payment commitment and rejected choices. Real Auth/Database tests cover contention, lost replies, a fresh Admin connection, delayed membership revocation and offline checkpoint reads. Public start/roll remain disabled; no live service/rules/store changes are introduced.

## Internal end-turn, city events and terminal results

end-kernel.cjs now executes the audited onlineTick/advanceTurn/endCheck/standings path with controlled synchronous UI/network adapters. It resets doubles, honors the original opening seat and bankrupt-seat skips, and prepares the next human roll or explicit jail/AI-worker boundary. It retains the original localized event pools, festival chance, cash payouts, grant tie ordering, lottery eligibility and event-before-final-ranking order. No profile/store rewards are issued. Completed games get private canonical standings and status over; member-only readResult exposes no game snapshot, deck or entropy.

The legacy online driver now checks terminal conditions before playing a resumed snapshot and immediately after advancing the round. This fixes a confirmed extra-turn bug at the timed limit; generated standalone/offline assets are updated. The source regression fails on the previous source and passes after the change. The source pin was re-audited for this terminal-check change; artwork, board, UI and custom rule values are untouched.

The internal endTurn command requires verified current authority/revision and no active roll/choice. It commits game state, event effects, an immutable end-transition slot, any next-owner checkpoint, final result if applicable, shared receipt and budget atomically. Retained slots reject replay after a rollback; they also fence property/roll requests at an already-consumed revision. The next jail checkpoint belongs to the next player, not the ending actor. AI turns remain paused for a trusted worker. Pending choices cannot be bypassed by ending.

A server-acknowledged preflight recovers existing receipts and only determines whether randomness will be needed. If needed, crypto.randomBytes supplies a fixed 16-word tape before the transaction; each callback recreates its bounded reader. Integer rejection sampling avoids modulo bias for event pools/lotteries. Tape exhaustion fails closed without partial cash effects and never samples more inside a callback. The private transition records accepted bound/value draws for audit. Competing/restarted instances recover the winning receipt rather than selecting another visible outcome. No-event turns work without entropy. A timeout is still uncertain, not rollback.

readResult requires fresh acknowledged membership, matching final revision/source/snapshot and the retained result. It is an internal method, not a new HTTP route. Terminal games cannot roll or edit property. Full source/browser parity, forced callback retries and real emulator contention/lost-reply/revocation tests cover this slice. Jail actions, cards, auctions, debt, replacement re-rolls, AI execution, trusted rewards, room incarnation/retention policy and full redacted live-client migration remain unfinished. Public v2 start/roll remain disabled. Existing deployment/release gates remain open.

## Internal jail and bail choices

Jail checkpoints now accept payBail or useBailPass through the internal choice handler. The audited original jailTurn supplies the fixed bail fee, fee-to-pot behavior, last-held pass/deck return, attempt counters and release flags. A paid fee or pass releases to the ordinary pre-roll stage without sampling dice; a freeing jail roll moves using the two ordinary dice and does not grant a doubles bonus or token re-roll. Existing turbo sampling/display is retained, but the original jail path does not apply turbo movement/star/taxi effects. This work preserves that behavior rather than changing a custom rule.

reserveJailRoll/loadJailRoll/recoverJailRoll are separate internal methods. Plans are typed jail, bound to the exact jail checkpoint hash as well as game/source/actor/revision, and use the same immutable revision slot/receipt/budget as ordinary rolls. A reserved jail outcome blocks switching to bail or a pass, including if the secondary lock index is missing. Ordinary reserve/commit methods cannot bypass the jail choice. commitJailRoll atomically consumes the saved outcome and applies one attempt, payment, movement and next checkpoint/receipt as appropriate. No public HTTP route/client button is added.

First/second failed attempts remain in jail and stop at post-roll management. Doubles escape free; a third failed attempt owes the source bail fee before moving. Insufficient mandatory bail pauses at debt with jailTurns=3 and a jail-action continuation marker; debt after release has a separate landing marker. Neither is silently written off or converted into automatic bankruptcy. Purchase continuations after release retain no-extra-roll/no-turbo-follow-up context. Unsupported debt/card/auction actions remain paused.

readDecision enriches a valid current jail boundary with source bail, affordable-cash flag, pass count and attempt number. Jail state must be at the Lockup with zero doubles and fewer than three prior attempts. Earlier test-only jail fixtures were corrected to put the flagged player on square 10; no product rule or source artwork changed. Shared sampler validation still rejects expired games and unauthorized identities.

Full source playTurnInner/jailTurn browser comparisons include every ordinary dice pair at all three attempts, paid/card choices, deck conservation, turbo behavior, mandatory bail debt and subsequent landing decisions. Forced callbacks and real Auth/Database races/lost replies/recreated services verify one fee/pass/attempt and no post-reservation switching. AI jail execution, debt liquidation/bankruptcy, card execution, auctions, replacement re-rolls, trusted rewards and full redacted client/production migration remain open. Public start/roll stay disabled; no live Firebase or store deployment is performed.

## Internal auction bidding and settlement

A declined property still pauses at the original auction boundary. The turn owner starts it with the internal startAuction choice. The source auction loop then derives seat order, bankrupt/low-cash skips, leader, active bidders and completion. Its UI adapter saves a bounded private transcript and pauses at each human bid. Replaying that transcript reconstructs the same source decision; no cash or property changes happen before settlement. Human bid intents accept drop (0) or the existing +10/+50/+100 buttons within current cash. Callers cannot choose a bidder, leader, property or transcript.

The internal auctionBid method authenticates the current bidder, which may differ from game.turn. Fresh decision reads use that same bidder authority. Every bid advances the room revision and commits the updated checkpoint/shared receipt together. A retry returns its historical acknowledgement, while changed IDs or stale/out-of-order bidders cannot bid twice. Normal turn commands retain turn-owner checks; an active auction cannot be restarted, bypassed with a roll/property edit, or ended.

Settlement reuses the source auction ownership/cash transfer and auction-win counters exactly once, then restores the original turn continuation. Doubles, cards, jail-release and turbo follow-up decisions retain their original context. All-drop/insufficient-cash auctions leave the property at the bank. The approved source's bounded loop remains in place; no new auction randomness is introduced.

AI bidding pauses at an explicit auction-ai worker boundary; this slice does not run the client AI or invent timeouts/forfeits for disconnected bidders. Disconnect/rejoin/forfeit policy and production leases still need full integration. Public start/action routes and live client wiring remain disabled. ## Internal debt liquidation, payment and bankruptcy

debtAction accepts sell/mortgage of a source-legal owned property, pay once the bill is funded, or bankrupt while cash is insufficient. The payer comes from the private debt boundary, including another player owing a card payment. Requests cannot supply an amount, creditor, payer, dice or replay history. Fresh decision reads and mutations require that payer's verified membership/seat and the current revision/checkpoint.

A suspended payment stores a private origin snapshot, source continuation and bounded debt-action tape. Re-executing the pinned synchronous source with accepted decisions reconstructs the current paused state before accepting another command. The published room is replaced atomically with the complete reconstructed result; it is not charged again from its partially updated state. No RNG is resampled. This preserves earlier card transfers, shield usage/logs, fixed repair bills, mandatory bail/attempts and subsequent movement. Asset sale/mortgage decisions stay paused until explicit Pay or bankruptcy. Building-bank/even-sale/mortgage constraints come from the original functions. The tape is limited to 256 accepted debt decisions; the private replay envelope is capped at 512 KiB.

The original pay/bankrupt functions and financial hooks now resume to completion, including cash minima, rent/creditor counters, source building liquidation, mortgage flags and Bail Pass transfer/deck returns. Bankruptcy with remaining players keeps the source busy phase; the internal end-turn adapter now accepts that finished bankrupt turn and advances normally. Last-player bankruptcy atomically records over status and the existing canonical standings/result. No profile currency/XP/store reward is issued.

Every liquidation/payment/estate change, next payer/checkpoint or result, revision and shared receipt commits together. Retries recover historical acknowledgements. New or stale requests cannot repeat a paid bill, card transfer, jail roll or estate distribution. A timeout is uncertain, not rollback; use the original operation ID. Debt cannot be bypassed with ordinary property edits, purchases, rolls or end-turn.

## Interrupted-action settlement and opt-in screen controls

Malformed original commands with valid room/ID/revision may also retire their ID; those IDs cannot later become a different valid command.
